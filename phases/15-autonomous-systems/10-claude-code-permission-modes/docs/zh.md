# Claude Code 作为自主 Agent：权限模式和自动模式

> Claude Code 暴露了七种权限模式。"plan" 在每个操作前询问，"default" 仅对有风险的操作询问，"acceptEdits" 自动批准文件写入但仍确认 Shell 执行，"bypassPermissions" 批准一切。自动模式（2026 年 3 月 24 日）用两阶段并行安全分类器替代了逐操作审批：一个单 Token 快速检查在每个操作上运行；被标记的操作触发思维链深度审查。操作预算通过 `max_turns` 和 `max_budget_usd` 强制执行。自动模式以研究预览形式发布——Anthropic 已明确声明分类器单独使用是不够的。

**类型：** 学习
**语言：** Python（标准库，两阶段分类器模拟器）
**前置条件：** Phase 15 · 01（长程 Agent），Phase 15 · 09（编码 Agent 全景）
**时间：** ~45 分钟

## 问题引入

> **【中文解读】** Claude Code 的权限模式是 Agent 安全控制的典型案例。四种模式：(1) Ask——每次操作需用户确认；(2) Edit——文件编辑自动批准，命令需确认；(3) YOLO——所有操作自动批准（危险）；(4) Plan——先规划后执行。这些模式反映了 Agent 自主性与安全性的基本权衡。

> **【拓展：claude code permission modes】** Claude Code 的权限设计体现了 2026 年编码 Agent 的安全最佳实践。关键原则：(1) 最小权限——默认只授予必要权限；(2) 渐进授权——用户可以根据信任度逐步放宽限制；(3) 审计追踪——所有操作都有日志；(4) 紧急停止——随时可以中断。这些原则同样适用于其他 Agent 系统的设计。

你机器上的自主编码 Agent 是一个独特的安全类别。攻击面是 Agent 能触及的一切——文件系统、网络、凭证、剪贴板、任何浏览器标签页、任何打开的终端。Bruce Schneier 等人公开指出：计算机使用 Agent 不是聊天机器人的"功能更新"，它们是一种具有新型风险特征的新型工具。

Claude Code 的权限系统是 Anthropic 的回答。不是一个"自主/不自主"开关，而是七种模式构成能力阶梯：plan → default → acceptEdits → ... → bypassPermissions。每种模式在速度和每操作审查之间有不同的权衡。自动模式（2026 年 3 月）添加了两阶段分类器，将审批从用户关键路径移到分类器判断安全的操作上，同时为分类器标记的操作保留审查层。

> **【中文解读】** 本节介绍了 AI Agent 的核心概念和实现方法。Agent 是 LLM 驱动的自主系统，能够观察环境、思考决策、执行行动并循环迭代直到完成目标。

工程问题：这个系统捕获什么，遗漏什么，给定任务实际上应该使用哪种模式？

## 核心概念

### 七种权限模式

| 模式 | 行为 | 何时使用 |
|---|---|---|
| `plan` | Agent 提出计划；用户批准整个计划；每个操作在执行前审查 | 不熟悉的任务；接近生产的代码；首次在仓库中使用 Agent |
| `default` | Agent 运行操作；对任何"有风险"的操作提示用户（Shell 执行、破坏性操作、网络调用） | 大多数交互式编码会话 |
| `acceptEdits` | 文件写入自动批准；Shell 执行和网络调用仍提示 | 跨多文件的重构 |
| `acceptExec` | Shell 命令在策划的允许列表内自动批准；写入自动批准 | 紧密内循环中每个 Shell 命令都是 `npm test` 或类似命令 |
| `autoMode` | 两阶段安全分类器；被标记的操作提升到审查 | 受限工作区中的长程无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许列表/拒绝列表 | 临时沙箱、CI 任务、研究脚本 |
| `bypassPermissions` | 批准一切 | 文档标注为"仅在您愿意丢弃的临时容器内" |

（以上名称匹配公开的 Claude Code 文档；"yolo" 是宽松中间地带的非正式简称。）

### 自动模式，一页讲清楚

自动模式（2026 年 3 月 24 日发布）是第一个将逐操作审批委托给模型的权限模式。结构：

1. **阶段 1 — 单 Token 分类器。** 在每个提议的操作上运行。廉价。返回"安全"或"标记"。设计为与主 Agent 循环并行运行，使批准的操作不会排队等待。
2. **阶段 2 — 二级策略/安全审查。** 仅在被标记的操作上运行。对操作、当前会话状态和声明任务执行聚焦的策略和安全评估。如果置信度低，升级到用户 HITL。

预算控制与分类器并存：

- `max_turns` — 会话中的总迭代次数。
- `max_budget_usd` — 金额上限，达到时终止会话。
- 每个工具的操作计数限制（不超过 N 次 `WebFetch` 调用等）。

### 系统捕获什么

- 直接的提示注入到工具输入中，其中注入的指令映射到已知的有风险操作形状。
- 重复的工具循环——分类器可以看到操作 N+1 与操作 N 几乎相同，连续五次。
- 在一个纯文件编辑会话中明显超出范围的 Shell 命令。

### 系统可能遗漏什么

- **微妙的提示注入**，在没有产生单个被标记操作的情况下调节行为。间接提示注入不是一个完全可修补的漏洞（OpenAI 准备性负责人，2025 年，关于浏览器 Agent——见第 11 课）。
- **语义级的不良行为。** 每个单独的操作看起来安全，但组合轨迹有害。分类器判断操作；它不会重新推导用户的意图。
- **通过合法渠道的数据泄露。** 将数据写入你拥有的文件，然后 `git push` 到公共仓库，是一系列允许的操作，其组合才是问题。

### 研究预览框架

Anthropic 将自动模式作为研究预览发布。文档明确说明分类器是一个层，不是解决方案：用户被期望将自动模式与预算、允许列表、隔离工作区和轨迹审计结合使用（第 12-16 课）。预览框架也反映了记录的评估-部署差距（第 1 课）——通过离线评估的分类器在用户上下文模糊的真实会话中可能表现不同。

### 这个阶梯在你的工作流中的位置

- 不熟悉的任务：从 `plan` 开始。阅读计划比回滚一次糟糕的运行更便宜。
- 已知的重构：`acceptEdits` 节省大量确认点击。
- 无人值守的后台运行：`autoMode` 仅在爆炸半径已测量的工作区内使用（没有凭证、没有生产挂载、没有未选择的出口）。
- 临时容器：`yolo` / `bypassPermissions` 可接受的条件是容器及其凭证是一次性的。

## 用框架实现

`code/main.py` 模拟两阶段分类器。阶段 1 是提议操作上的廉价关键词规则；阶段 2 是较慢的多规则审查器。驱动器输入一个简短的合成轨迹（安全操作、提示注入尝试、重复循环）并展示分类器在哪里捕获和遗漏。

## 产出物

`outputs/skill-permission-mode-picker.md` 将任务描述匹配到正确的权限模式、预算上限和所需隔离。

## 术语速查表

| 术语 | 人们常说的 | 实际含义 |
|---|---|---|
| 权限模式 (Permission Mode) | "Agent 能做多少" | 控制逐操作审批的七种命名策略之一 |
| 计划模式 (plan mode) | "做什么前先问" | Agent 编写计划；用户批准后再执行 |
| acceptEdits | "让它写文件" | 文件写入自动批准；Shell 执行仍提示 |
| autoMode | "自动审批" | 两阶段安全分类器；被标记的操作升级 |
| bypassPermissions | "完全 YOLO" | 批准一切；用于临时容器 |
| 阶段 1 分类器 (Stage 1 Classifier) | "快速 Token 检查" | 对提议操作的单 Token 规则；并行运行 |
