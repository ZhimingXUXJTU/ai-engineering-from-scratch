# 长时间运行的后台 Agent：持久执行

> 生产长程 Agent 不在 `while True` 中运行。每个 LLM 调用成为带有检查点、重试和重放的活动。Temporal 的 OpenAI Agents SDK 集成于 2026 年 3 月 GA。Claude Code 例程（Anthropic）运行计划性的 Claude Code 调用而无需持久本地进程。会话在人类输入时暂停、在部署后存活、并从以 `thread_id` 为键的最新检查点恢复。在新的人体工程学背后是一个旧模式——工作流编排——带有一个新输入：LLM 调用作为必须在恢复时确定性重放的非确定性活动。

**类型：** 学习
**语言：** Python（标准库，最小持久执行状态机）
**前置条件：** Phase 15 · 10（权限模式），Phase 15 · 01（长程 Agent）
**时间：** ~60 分钟

## 问题引入

> **【中文解读】** 持久执行确保 Agent 任务在故障后能恢复。传统 Agent 在内存中运行，进程崩溃意味着从头开始。持久执行将状态保存到外部存储（数据库、文件系统），任何时刻都可以从最近的检查点恢复。Temporal 和 LangGraph 是实现持久执行的两个主流框架。

> **【拓展：durable execution】** 持久执行对长时间运行的 Agent 至关重要。如果一个需要运行 2 小时的 Agent 在第 90 分钟崩溃，没有持久执行就意味着重新开始。Temporal 通过事件溯源实现持久工作流，LangGraph 通过检查点实现持久状态图。2026 年的最佳实践是每个重要步骤后自动保存检查点。

考虑一个运行四个小时的 Agent。它调用三个工具，两次提示用户，并进行四十次 LLM 调用。运行到一半时，它运行的主机重启了。会发生什么？

- 在一个天真的 `while True` 循环中：一切丢失。运行从头开始。三个工具调用（有真实副作用）再次执行。用户再次被提示已经批准的事情。四十次 LLM 调用重新计费。
- 在持久执行中：运行从最近的检查点恢复。已完成的活动不重新执行；它们的结果从持久日志重放。用户不重新批准已经批准的事情。已完成的 LLM 调用不重新计费。

> **【中文解读】** 本节介绍了 AI Agent 的核心概念和实现方法。Agent 是 LLM 驱动的自主系统，能够观察环境、思考决策、执行行动并循环迭代直到完成目标。

这是工作流引擎已发布十年的相同模式（Temporal、Cadence、Uber 的 Cherami）。新的是 LLM 调用现在是一种活动——非确定性、昂贵、有副作用——它们干净地适配这个模式。

本课的贯穿主题：长程可靠性衰减（METR 观察到"35 分钟退化"——成功率随时间范围大致二次方下降）。持久执行使运行时间长于可靠性概况支持的，如果设计正确这是一种安全失败的新方式，如果设计错误则是不安全的。

## 核心概念

### 活动、工作流和重放

- **工作流 (Workflow)**：确定性编排代码。定义活动序列、分支、等待。必须是确定性的，以便从事件日志重放时不会出现令人惊讶的分歧。
- **活动 (Activity)**：一个非确定性、可能失败的工作单元。LLM 调用、工具调用、文件写入、HTTP 请求。每个活动记录其输入和（完成后）输出。
- **事件日志 (Event Log)**：持久后端存储。每个活动的启动、完成、失败、重试以及每个工作流决策都被记录。
- **重放 (Replay)**：恢复时，工作流代码从头重新运行；每个已完成的活动返回其记录的结果而不重新执行。只有未完成的活动才实际运行。

这与 React 针对虚拟 DOM 重新渲染，或 Git 从提交重建工作树是相同的形态。编排器中的确定性使持久化变得廉价。

### 为什么 LLM 调用适配该模式

LLM 调用：
- 非确定性（temperature > 0；即使 temperature 0 在模型版本间漂移）。
- 昂贵（金钱和延迟）。
- 可能失败（速率限制、超时）。
- 有副作用（如果它们调用工具）。

这正是活动概况。将每个 LLM 调用包装为活动给你带来指数退避的重试、跨重启的检查点和可重放的调试追踪。

### 以 `thread_id` 为键的检查点

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code 例程都收敛到相同的 API 形状：一个 `thread_id`（或等效物）标识会话；每个状态转换持久化到后端（PostgreSQL 默认，SQLite 用于开发，Redis 用于缓存）；恢复读取最新检查点。

后端选择很重要：

- **PostgreSQL**：持久、可查询、在部署后存活。LangGraph 的默认。
- **SQLite**：仅用于本地开发；跨主机丢失数据。
- **Redis**：快速但临时，除非配置 AOF/快照。
- **Cloudflare Durable Objects**：透明分布式；以唯一键为范围；存活数小时到数周。

### 人类输入作为一等状态

先提议后提交（第 15 课）需要一个持久的"等待人类"状态。工作流暂停，外部队列持有待处理请求，批准从该点精确恢复。没有持久性这是尽力而为；有了它，隔夜的批准到达后，工作流在早上继续。

### 35 分钟退化

METR 观察到每个被测量的 Agent 类别都显示出约 35 分钟连续操作后的可靠性衰减。将任务持续时间加倍大约四倍化失败率。持久执行不修复这个问题；它让你运行长于可靠性概况支持的时间。安全的模式是将持久性与重新进入时需要新 HITL 的检查点结合，以及限制总计算量的预算终止开关（第 13 课），不管挂钟时间多长。

### 持久执行何时是错误的答案

- 少于几分钟且没有人类输入的运行。开销 > 收益。
- 严格的只读信息检索。
- 正确性需要在单个上下文窗口内端到完成的任务（某些推理任务；某些一次性生成）。

## 用框架实现

`code/main.py` 用标准库 Python 实现一个最小持久执行引擎。它支持：

- `@activity` 装饰器，将输入和输出记录到 JSON 事件日志。
- 一个排序活动的工作流函数。
- 一个 `run_or_replay(workflow, event_log)` 函数，重放已完成的活动而不重新执行它们。

驱动器模拟一个三活动工作流，中途崩溃，并展示 (a) 天真的重试重新执行一切对比 (b) 重放只运行缺失的活动。

## 产出物

`outputs/skill-durable-execution-review.md` 审查一个提议的长运行 Agent 部署的正确持久执行形态：活动、确定性、检查点后端、人类输入状态和恢复时的 HITL 策略。

## 术语速查表

| 术语 | 人们常说的 | 实际含义 |
|---|---|---|
| 工作流 (Workflow) | "Agent 的脚本" | 确定性编排代码；可从事件日志重放 |
| 活动 (Activity) | "一个步骤" | 非确定性单元（LLM 调用、工具调用）；前后记录 |
| 事件日志 (Event Log) | "后端存储" | 每个状态转换的持久记录 |
| 重放 (Replay) | "恢复" | 重新运行工作流；已完成活动返回记录结果而不重新执行 |
| 检查点 (Checkpoint) | "保存点" | 以 thread_id 为键的持久化状态；恢复时取最新 |
| thread_id | "会话键" | 限定持久状态的标识符 |
| 35 分钟退化 | "可靠性衰减" | METR：成功率随时间范围大致二次方下降 |
| 非确定性 (Non-determinism) | "重放时漂移" | 挂钟、随机、LLM 输出；必须作为副作用注册 |
