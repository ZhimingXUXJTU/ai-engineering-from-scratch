# 检查点与回滚

> 每个图状态转换都持久化。当工作器崩溃时，其租约过期，另一个工作器从最新检查点接管。Cloudflare Durable Objects 跨数小时或数周保持状态。先提议后提交（第 15 课）为每个操作定义了回滚计划。操作后验证闭合了循环。EU AI 法案第 14 条使有效的人类监督对高风险系统成为强制性——在实践中这意味着检查点必须可查询、回滚必须经过演练、审计追踪必须在部署后存活。尖锐的失败模式：没有幂等键和前置条件检查，瞬态故障后的重试可能双重执行已批准的操作。操作后验证就是捕获这个的。

**类型：** 学习
**语言：** Python（标准库，检查点和回滚状态机）
**前置条件：** Phase 15 · 12（持久执行），Phase 15 · 15（先提议后提交）
**时间：** ~60 分钟

## 问题引入

> **【中文解读】** 检查点和回滚机制允许 Agent 在执行过程中保存状态快照，出错时恢复到之前的良好状态。这类似于数据库的事务和 Git 的版本控制。检查点保存在关键节点（如修改文件前），回滚在检测到错误时执行。LangGraph 的内置检查点和 Git 的 revert 是两个典型实现。

> **【拓展：checkpoints rollback】** 检查点-回滚是可靠 Agent 系统的基础设施。实现选择：(1) 文件系统级——使用 Git 或快照保存文件状态；(2) 数据库级——使用事务保证数据一致性；(3) 应用级——Agent 自己管理检查点（如 LangGraph）。关键权衡是检查点粒度——太细会增加开销，太粗会丢失更多工作。

持久执行（第 12 课）使崩溃的 Agent 可恢复。先提议后提交（第 15 课）使批准的操作可审计。本课将它们连接起来：当一个已批准的操作部分执行、崩溃并恢复时会发生什么？回滚何时运行，针对什么状态？

真实系统的接线方式各不相同：

> **【中文解读】** 本节介绍了 AI Agent 的核心概念和实现方法。Agent 是 LLM 驱动的自主系统，能够观察环境、思考决策、执行行动并循环迭代直到完成目标。

- **LangGraph** 将每个图状态转换检查点到 PostgreSQL。在工作器崩溃时，租约释放，另一个工作器从最新检查点恢复。工作流在 `interrupt()` 处暂停，`interrupt()` 本身也被持久化。
- **Cloudflare Durable Objects** 跨数小时或数周保持每个键的状态。将计算与已批准操作的存储共置。
- **Microsoft Agent Framework** 在工作流 API 中暴露 `Checkpoint` 原语；重放加幂等性覆盖重试。

在每个案例中，真正有效的组合是：幂等键（防止双重执行）+ 前置条件检查（状态仍与批准时一致）+ 操作后验证（副作用实际发生了）+ 验证失败时回滚。

## 核心概念

### 每个转换都持久化

图状态转换是将工作流从一个命名状态移动到另一个命名状态的任何步骤。天真的实现只在特定提交点持久化；生产实现持久化每个转换。成本（一些额外的写入）相对于可靠性增益（重放可以在任何位置着陆，租约恢复是精确的）很小。

### 租约恢复

当工作器崩溃时，工作流不会丢失；租约（该工作器正在执行此运行的短期声明）只是过期。另一个工作器获取最新检查点并恢复。租约机制是让生产系统在滚动部署中存活而不丢失进行中工作的关键。

### 幂等性加前置条件

仅靠幂等性不够。考虑：一个工作流被批准"在余额 > $1000 时从 A 转账 $100 到 B。"工作流已提交，执行中途崩溃，然后恢复。如果只检查幂等键，执行恢复，转账运行一次（正确）。但考虑在崩溃和恢复之间，A 的余额通过另一个工作流降到 $500。幂等检查仍然通过；前置条件不通过。没有前置条件检查，我们就会透支。

每个有后果的操作都需要两者：

- **幂等键**：防止双重执行。
- **前置条件检查**：确认状态仍与批准时一致。

### 操作后验证

"工具返回 200"不是验证。真正的验证重新读取目标状态并确认副作用实际发生。模式：

- 数据库更新：`UPDATE ... RETURNING *`，然后断言返回的行匹配预期状态。
- 邮件发送：提交后检查已发送文件夹中的消息 ID。
- 文件写入：回读文件并计算哈希。
- API 调用：对目标资源执行后续 `GET`。

如果验证失败，工作流处于已知不良状态。回滚启动。

### 回滚计划

先提议后提交（第 15 课）中每个有后果的操作都携带回滚计划。类型：

- **带内回滚**：直接反转副作用（`INSERT` 后的 `DELETE`，发送后的发送更正邮件）。
- **补偿事务**：一个抵消原始操作的新操作（标准 SAGA 模式）。
- **带外回滚**：告警人类，暂停工作流，将不良状态留待调查。

空操作回滚（"我们无法撤销这个"）必须在提议中命名。没有回滚的操作在提交时需要更强的 HITL（第 15 课挑战-响应）。

### EU AI 法案第 14 条的操作解读

第 14 条要求高风险系统的"有效人类监督"。在操作层面，实现者将其解读为：

- 检查点可由审计员查询。
- 回滚经过演练（至少端到端测试一次）。
- 审计追踪在部署后存活（检查点后端不是临时的）。
- 失败的验证有告警，不是静默记录。

一个在提交中途崩溃、恢复、并在没有验证 + 回滚路径的情况下完成副作用的工作流不能通过第 14 条测试。

### 尖锐的失败模式：双重执行

这个领域最常见的生产事件：

1. 操作已批准，幂等键 k。
2. 提交开始，执行，返回 200。
3. 工作流在持久化"已提交"状态前崩溃。
4. 工作流恢复；看到"已批准但未提交"；重新执行。
5. 副作用触发两次。

缓解措施：在执行前持久化"进行中"意图，用幂等键执行，然后仅当操作后验证成功后标记"已提交"。如果操作触发但状态写入失败，你知道要验证并在必要时重新触发。如果状态写入成功但操作失败，你验证并通过恢复路径精确触发一次。

## 术语速查表

| 术语 | 人们常说的 | 实际含义 |
|---|---|---|
| 检查点 (Checkpoint) | "保存点" | 每个图状态转换持久化到持久存储 |
| 租约 (Lease) | "工作器声明" | 工作器正在执行某运行的短期声明；崩溃时过期 |
| 前置条件 (Precondition) | "状态门控" | 断言状态仍与批准的操作一致 |
| 操作后验证 (Post-action Verify) | "回读检查" | 确认副作用在目标系统中实际发生 |
| 带内回滚 (In-band Rollback) | "直接撤销" | 用逆操作反转副作用 |
| 补偿事务 (Compensating Transaction) | "SAGA 撤销" | 抵消原始操作的新操作 |
| 先标记完成 (Mark-as-done-first) | "状态写入顺序" | 在从提交返回前持久化已提交状态 |
| 第 14 条 (Article 14) | "EU AI 法案人类监督" | 操作层面：可查询检查点、演练回滚、可审计追踪 |
