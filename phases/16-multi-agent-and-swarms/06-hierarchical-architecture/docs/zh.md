# 层次化架构及其失败模式 | 分层

> 层次化是监督者的嵌套。管理者 Agent 在子管理者之上，子管理者在工作器之上。CrewAI 的 `Process.hierarchical` 是教科书版本：一个 `manager_llm` 动态委派任务并验证输出。LangGraph 的等价物是 `create_supervisor(create_supervisor(...))`。当任务是真实的组织结构图时，这是自然的模式。但它也是最容易崩溃为管理循环的模式——管理者 Agent 分配工作不当、误解子输出或无法达成共识。顺序模式通常比它更好。

> **【中文解读】** 本节介绍了分层架构——多层编排器的嵌套组织结构，适用于复杂任务的递归分解。

> **【拓展：hierarchical architecture→具体应用】** 分层架构将监督者模式递归嵌套——顶层主管分配给中层管理者，中层管理者再分配给底层工作者。这类似于人类组织的层级结构。2026 年的实践表明，2-3 层的层次是最优的——太浅（1层）导致主管过载，太深（4+层）导致信息失真和延迟增加。


**类型：** 学习 + 构建
**语言：** Python（标准库）
**前置条件：** 第 16 阶段 · 05（监督者模式）
**时间：** ~60 分钟

## 问题引入

一旦监督者模式理解了，自然的下一步是"如果工作器本身也是监督者会怎样？"团队有子团队；公司有部门的部门。层次化架构反映了这一点。

问题在于：LLM 管理者与人类管理者不同。人类管理者对其下属了解什么有稳定的先验。LLM 管理者每轮从其上下文中的任何内容重新推理整个组织。上下文中的微小漂移，整棵树就会错误分配工作。

## 核心概念

### 形状

```
                 管理者
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       子管理者 A         子管理者 B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点规划、委派和综合。只有叶子节点做工作。

### 优势

- **清晰的组织映射。** 如果真实任务是部门化的（"法律审查文档、财务审查文档、工程审查文档，然后为高管总结"），层次结构是明确的。
- **本地摘要。** 每个子管理者在顶层管理者看到之前综合其团队的输出。顶层管理者看到三个子管理者摘要，而不是十五个工作器输出。

### 劣势

2026 年事后分析持续发现的三个失败模式：

1. **任务分配错误。** 管理者阅读目标，幻觉出一个分解，并委派给错误的子管理者。因为子管理者服从地处理分配给它的任务，错误只在顶层综合时浮出——比人类能捕获的晚了一层。
2. **输出误解。** 子管理者返回"无法验证声明 X。"顶层管理者总结为"声明 X 未确认。"每一层意思都在漂移。
3. **共识循环。** 两个子管理者不一致；顶层管理者要求它们协调；它们向下重新委派；工作器重新运行；子管理者返回略有不同的答案；循环。CrewAI 的 `Process.hierarchical` 通过步骤限制来防范，但限制本身现在是一个超参数。

### 决定性问题

顺序（线性流水线）vs 层次化：你的任务真的有独立的子团队吗，还是一个伪造成树的线性流程？如果是后者，使用顺序模式。如果是前者，使用层次化，但要预算明确的对账规则。

### CrewAI 的实现

`Process.hierarchical` 在专业团队之上连接一个管理者 LLM。管理者：

- 接收顶层任务
- 将子任务分配给团队
- 评估团队输出
- 决定是接受、重新委派还是迭代

文档：https://docs.crewai.com/en/introduction（查找核心概念下的"Hierarchical Process"）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内部监督者有自己的图；外部监督者将内部图视为不透明节点。这比 CrewAI 更容易调试（你可以分别单步调试每个图），但更难表达树的动态重塑。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 动手构建

`code/main.py` 运行三层层次结构：

- 顶层管理者：将任务拆分为"工程"和"法律"分支
- 工程子管理者：拆分为"前端"和"后端"工作器
- 法律子管理者：一个工作器

演示对比了正常路径（所有人一致）与**扰动路径**，其中顶层管理者的分解将"法律"错误标记为"财务"，观察错误级联——子管理者服从地做财务工作，顶层综合者报告财务发现，原始法律问题未被处理。

运行：

```
python3 code/main.py
```

输出显示两条路径，并排对比"被要求的"与"被交付的"。

## 用框架实现

`outputs/skill-hierarchy-fitness.md` 评估给定任务是否应该使用层次化、顺序化还是扁平监督者。输入：任务描述、组织结构、对账预算。输出：模式推荐及需要防范的具体失败模式。

## 产出物

如果你发布层次化架构：

- **将树深度限制在 2。** 三层已经隐藏了大部分错误使其脱离可观察性。
- **明确对账预算。** 在顶层管理者必须提交之前设置最大轮次。通常是 2。
- **每次综合的出处。** 每个节点的摘要必须引用哪些叶子输出产生了它。
- **分解漂移警报。** 记录每步管理者的分解；与用户查询比较。如果分解不再覆盖查询，触发警报。

## 练习题

1. 运行 `code/main.py`，比较正常与扰动路径。需要多少层管理者交接，顶层输出才完全偏离用户问题？
2. 添加第三层（顶层 → 子 → 子子 → 工作器）。随着深度增长，测量扰动路径自我纠正与完全偏离的频率。
3. 在每个子管理者处实现一个"金丝雀"工作器，始终被问原始用户问题不变。当金丝雀答案与综合答案不一致时，管理者应该如何反应？
4. 阅读 CrewAI 的 `Process.hierarchical` 文档。识别 CrewAI 应用的一个具体护栏（步骤限制、manager_llm 约束）并描述它针对什么失败模式。
5. 比较嵌套的 LangGraph 监督者与 CrewAI 层次化。哪个使对账循环更便宜地检测？

## 术语速查表

| 术语 | 人们常说的 | 实际含义 |
|------|-----------|---------|
| 层次化 | "组织结构图模式" | 监督者之上的监督者；只有叶子节点做工作。 |
| 管理者 LLM | "老板" | 在内部节点分解、分配和验证的 LLM。 |
| 分解漂移 | "老板偏离了主题" | 顶层管理者的拆分不再覆盖原始问题。 |
| 对账循环 | "无尽的会议" | 子管理者不一致；顶层重新委派；工作器重新运行；循环直到预算耗尽。 |
| 深度-2 上限 | "不要超过 2 层" | 经验护栏：3+ 层会崩溃可观察性。 |
| 金丝雀问题 | "每层的基准真相" | 始终被问原始查询不变的工作器，用于检测漂移。 |
| 出处链 | "谁说了什么" | 从每次综合追溯到产生它的叶子输出的追踪。 |
