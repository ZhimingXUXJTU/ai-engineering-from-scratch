# 监督者/编排器-工作器模式 | 主管/编排器-工作器模式

> 一个主导 Agent 规划和委派；专业化工作器在并行上下文中执行并汇报。这是 Anthropic Research 系统背后的模式（Claude Opus 4 作为主导，Sonnet 4 作为子 Agent），在内部研究评估上比单 Agent Opus 4 提升 90.2%。Anthropic 的工程博文报告称 BrowseComp 上 80% 的方差仅由 token 使用量解释——多 Agent 胜出主要因为每个子 Agent 获得全新的上下文窗口。本课从原语构建监督者模式，并涵盖 2026 年来自生产部署的工程经验。

> **【中文解读】** 一个主管 Agent 规划并委派任务；专业化工作器在并行上下文中执行并汇报。这是 Anthropic Research 系统背后的模式（Claude Opus 4.6 主管，Sonnet 4.5 子 Agent），在内部研究评估上比单 Agent Opus 4.6 提升 90.2%。核心洞察：多 Agent 胜出主要因为每个子 Agent 获得独立的上下文窗口——80% 的 BrowseComp 方差仅由 Token 使用量解释。

> **【拓展：Supervisor 模式 → Claude DevFleet】** Claude Code 的多 Agent 编排工具 Claude DevFleet 就是 Supervisor 模式的实现——一个主 Agent 分解任务，派发到多个隔离的 worktree 中的子 Agent 并行工作，最后汇总结果。Anthropic 的生产 Research 系统也使用此模式。

**类型：** 学习 + 构建
**语言：** Python（标准库，`threading`）
**前置条件：** 第 16 阶段 · 04（原始模型）
**时间：** ~75 分钟

## 问题引入

研究是单 Agent 系统失败的典型任务。你问"2023 到 2026 年间多 Agent 系统发生了什么变化？"单 Agent 顺序读取五篇论文，用一半上下文填充文本，然后必须同时对所有论文进行推理。到第五篇时它已经忘记了第一篇。它无法并行化。

监督者模式解决了这个问题：一个主导 Agent 规划搜索，将每个子问题委派给工作器，然后综合。每个工作器为自己的狭窄问题获得独立的 20 万 token 窗口。主导 Agent 永远不会看到原始论文——只看到工作器摘要。

Anthropic 的生产 Research 系统报告比单 Agent Opus 4 提升 +90.2%。同一博文指出 BrowseComp 方差的 80% 由*token 使用量单独*解释。每个子 Agent 的全新上下文是主要机制。

## 核心概念

### 模式

```
                 ┌──────────────┐
                 │   主导       │  规划、分解、
                 │  (Opus 4)    │  综合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 工作器1 │  │ 工作器2 │  │ 工作器3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         全新         全新         全新
         上下文       上下文       上下文
```

主导 Agent 永远不阅读原始材料。工作器永远看不到彼此的工作，直到主导 Agent 综合。每个箭头是带有狭窄产物的交接。

### 为什么它赢

三个机制：

1. **每个子 Agent 的全新上下文。** 探索"FIPA-ACL 遗产"的工作器不会携带主导 Agent 规划时消耗的 4 万 token。它为一个问题获得 20 万 token 的窗口。
2. **通过提示词专业化。** 主导 Agent 的提示词是"分解和综合"，不是"研究"。每个工作器的提示词是狭窄的："找出 X 中发生了什么变化。"聚焦的提示词产生聚焦的输出。
3. **并行性。** 工作器并发运行。挂钟时间大约是 `max(工作器时间) + 规划 + 综合`，而不是 `sum(工作器时间)`。

### 工程经验（Anthropic 2025）

Anthropic 博文列出了几条 2026 年仍然相关的生产经验：

- **根据查询复杂度调整工作量。** 简单查询：一个 Agent，3-10 次工具调用。复杂查询：10+ 个 Agent。主导 Agent 必须评估这一点，而不是调用者。
- **先宽后窄。** 先分解为宽泛的子问题，如果答案值得深入则每个子问题再生成更多工作器。
- **彩虹部署 (Rainbow deployments)。** Agent 是长时间运行且有状态的。传统的蓝绿部署不适用。Anthropic 使用彩虹：新版本的渐进推出，同时旧版本排空。
- **Token 使用量占主导。** 多 Agent 的 token 消耗约是单 Agent 的 15 倍。只在任务价值证明成本合理时运行。

### LangGraph 的转向

LangGraph 最初发布了一个带有高级 `create_supervisor` 辅助函数的 `langgraph-supervisor` 库。2025 年 LangChain 将推荐改为直接通过工具调用实现监督者模式，因为工具调用对*监督者看到什么*（上下文工程）提供了更好的控制。库仍然有效；文档现在推荐工具调用形式。

### 失败模式

- **主导 Agent 幻觉计划。** 如果主导 Agent 生成的子问题没有分解真正的问题，工作器会在错误目标上做精确研究。
- **工作器过度探索。** 没有显式范围边界，工作器会超出其分配的子问题漂移，污染综合步骤。
- **综合冲突。** 两个工作器返回矛盾的事实。主导 Agent 必须重新询问（增加一轮）或明确标注分歧。静默选择一方是最糟糕的失败：用户永远不知道发生了分歧。

### 什么时候不用监督者

- **顺序任务。** 如果步骤 2 确实需要步骤 1 的输出，并行性毫无收益。使用流水线（CrewAI Sequential、LangGraph 线性图）。
- **简单查询。** 单 Agent 更快更便宜。在生成工作器之前使用主导 Agent 的"调整工作量"检查。
- **严格确定性。** 监督者使用 LLM 选择的委派。当审计/重播比适应性更重要时，静态图更好。

## 动手构建

`code/main.py` 使用 `threading` 实现了一个三个并行工作器的监督者。主导 Agent 将查询分解为子问题，工作器在每个子问题上并发运行，主导 Agent 综合。没有真正的 LLM——工作器是脚本化的，模拟获取和摘要。

关键结构：

- `Lead.plan(query)` 将查询拆分为 3 个子问题。
- `Worker.run(sub_q)` 返回一个假的摘要（在生产中可以是任何使用工具的 Agent）。
- `Lead.run(query)` 在线程中启动工作器，等待，然后综合。

运行：

```
python3 code/main.py
```

输出显示计划、带开始/结束时间戳的并行工作器追踪，以及最终综合。你可以看到挂钟时间的优势：三个 0.3 秒的工作器在大约 0.35 秒内运行，而不是 0.9 秒。

## 用框架实现

`outputs/skill-supervisor-designer.md` 接收用户查询并生成监督者模式设计：主导系统提示词、工作器角色、子问题分解规则和综合模板。在构建新的研究型 Agent 系统之前使用此技能。

## 产出物

部署监督者模式前的检查清单：

- **模型配对。** 主导 Agent 使用推理级模型（Opus 级、`o3` 级）。工作器使用更快、更便宜的模型（Sonnet、`o4-mini`）。
- **工作器超时。** 任何超过中位运行时间 2 倍的工作器被终止；主导 Agent 以更窄的范围重新生成或继续。
- **每个工作器的 token 上限。** 硬限制（比如预期综合输入的 10 倍），防止失控工作器耗尽预算。
- **可观察性。** 追踪主导 Agent 的计划、每个工作器的工具调用和综合。这是任何事后调试的基础。
- **彩虹推出。** 有状态长时间运行的 Agent 需要渐进版本过渡，而非热替换。

## 练习题

1. 运行 `code/main.py`，然后修改主导 Agent 生成 5 个工作器而不是 3 个。观察挂钟效果。在此演示中，什么工作器数量下生成开销超过并行节省？
2. 实现工作器超时：杀死任何运行超过 0.5 秒的工作器，让主导 Agent 综合剩余结果。你需要什么可观察性才能知道工作器被截断了？
3. 在主导 Agent 的综合中添加冲突检测步骤：如果两个工作器返回矛盾的答案，主导 Agent 记录分歧而不是选择一方。如何在不调用 LLM 的情况下检测矛盾？
4. 阅读 Anthropic 的 Research 系统工程博文。列出这个玩具演示需要采用的三条实践才能在生产中运行。
5. 比较 LangGraph 的 `create_supervisor`（旧版）与新的工具调用推荐。哪个对监督者看到什么提供更好的控制？为什么 Anthropic 明确只将子答案而非原始工作器上下文传递到综合中？

## 术语速查表

| 术语 | 人们常说的 | 实际含义 |
|------|-----------|---------|
| 监督者 (Supervisor) | "主导 Agent" | 规划、委派和综合的编排器 Agent。自己不做工作。 |
| 工作器 (Worker) | "子 Agent" | 由监督者以狭窄范围和独立上下文窗口调用的聚焦 Agent。 |
| 编排器-工作器 | "监督者模式" | 同一件事，不同名称。2026 年文献两者都用。 |
| 全新上下文 | "干净窗口" | 工作器的上下文从其系统提示词和分配的问题开始，而非主导 Agent 的历史。 |
| 彩虹部署 | "渐进推出" | 长时间运行的有状态 Agent 需要版本化排空和替换，而非蓝绿。 |
| Token 主导 | "上下文是变量" | Anthropic 数据显示研究评估方差的 80% 来自使用的总 token，而非模型选择。 |
| 调整工作量 | "Agent 数量匹配复杂度" | 主导 Agent 评估查询难度，相应地生成 1 或 10+ 个工作器。 |
| 综合冲突 | "工作器不一致" | 两个工作器返回矛盾的事实；主导 Agent 必须揭示分歧，而非静默选择一方。 |
