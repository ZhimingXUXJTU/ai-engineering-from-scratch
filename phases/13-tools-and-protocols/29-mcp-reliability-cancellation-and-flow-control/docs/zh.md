# MCP 可靠性、取消与流控

> 请求 ID 只负责关联消息。它不能让副作用变得安全、不能停掉一个 worker、也保护不了流不被慢消费者拖垮。

> **【中文解读】** 本课基于 MCP 2026-07-28 规范，讲分布式系统里最贵的那些 bug：取消竞态、双时钟超时、幂等重试、背压、重连风暴。核心立场：MCP 只定义消息和传输行为；时间预算、业务幂等、有界队列、重试分类、持久 Task 状态、重连与重取策略仍然归你的应用所有。

> **【拓展：MCP→分布式系统工程】** 取消信号与传输绑定、完成/取消竞态、空闲+绝对双超时、幂等键、事务性发件箱、背压、抖动退避——每个概念都是分布式系统的经典课题。本课的特殊性在于把它们放进 MCP 的具体语境：stdio 上取消是一条通知，Streamable HTTP 上取消是关闭响应流，`tasks/cancel` 面向持久 Task。

## 学习目标

- 为 stdio 和 Streamable HTTP 实现各自正确的取消信号。
- 解决"完成与取消"的竞态，且在取消之后不再发送消息。
- 把请求取消与持久 `tasks/cancel` 语义区分开。
- 基于副作用和显式幂等键构建重试决策。
- 给进度队列设界，同时保住最终响应。
- 通过重连、权威重取和带抖动的退避恢复流。

## 问题引入

快乐路径（happy path）藏着最昂贵的分布式系统 bug。

客户端调用一个工具。服务器开工。进度到来。代理缓冲了流。客户端到达超时并断开。服务器一毫秒之后完成。客户端换一个新的 JSON-RPC id 重试。变更执行了两次。

每个组件在本地都行为正确，系统在全局上失败了。

MCP 定义消息和传输行为，但以下事项仍然归你的应用所有：

- 时间预算；
- 业务幂等；
- 有界队列；
- 重试分类；
- 持久任务状态；
- 重连与重取策略。

本课把这些决策做进一个确定性模拟器。没有 sleep、没有 socket、没有随机失败：你直接控制取消事件的顺序。还有一个同步线程测试，逼两个账本客户端竞争同一个幂等键。

> **【中文解读】** "局部全对、全局失败"是分布式系统的标志性事故模式。本课模拟器的价值在于把无法复现的时序问题变成确定性的、可以反复重放的事件顺序。

## 请求取消是绑定传输方式的

意图在每个传输上都一样：客户端不再需要一个在途结果。线上信号却是不同的。

### stdio

stdio 使用一条共享的双向通道。客户端发送一条通知：

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}
```

这条通知是发后即忘的，服务器不会为它发出任何 JSON-RPC 响应。

服务器应当停止工作、释放资源，并避免为已取消的请求发送响应。当请求未知、已经完成或无法安全停止时，可以忽略取消。

畸形、未知和已完成的取消通知一律忽略——把这些竞态变成新错误只会制造更多竞态。

### Streamable HTTP

现代 Streamable HTTP 给每个请求独立的 HTTP 响应或 SSE 响应流。客户端通过关闭该请求的响应流来取消。

不要为普通 HTTP 请求 POST `notifications/cancelled`。流的关闭就是取消信号。

服务器一旦观察到断开，就应停止工作，并且不得再为该请求发送任何消息。

### 服务器方向的取消很窄

服务器不会用 `notifications/cancelled` 去取消任意的客户端调用。在 stdio 上，服务器方向的取消仅保留用于终止一个 `subscriptions/listen` 请求。把这条路径与普通的客户端请求取消分开。

> **【中文解读】** 一张速查表：stdio 取消 = 发一条 `notifications/cancelled` 通知；HTTP 取消 = 关闭该请求的响应流；服务器取消（仅 stdio、仅订阅）= 通知终止 `subscriptions/listen`。混用任何一种信号都是规范错误。

## 取消是一场竞态

两种事件顺序都是合法的。

### 取消获胜

```text
request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response
```

### 完成获胜

```text
request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification
```

客户端也必须忽略自己已放弃请求的迟到响应。网络延迟意味着双方都无法证明对方先观察到哪个事件。

```figure
mcp-reliability-race
```

本课的 `RequestCoordinator` 为每个请求只存一个终态。取消之后 `complete()` 不再返回响应；迟到的取消也改变不了已完成的记录。

> **【中文解读】** 竞态的对称性是关键：服务器可能在取消后还想发响应（必须压掉），客户端可能在放弃后还收到响应（必须忽略）。任何一侧"好心补发/补收"都会破坏协议。

## 超时需要两个时钟

只有一个不活动计时器是不够的。

设两个上限：

1. **空闲超时。** 请求多久没有产生有用活动。
2. **最大超时。** 从请求开始的绝对墙钟预算。

进度可以重置空闲时钟，但绝不能移除最大期限。

```text
start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms
```

在 1500 ms 时，请求仍然活跃，因为最近的进度只有 300 ms 大。在 2000 ms 时，即使 1999 ms 刚到一条进度，最大期限也会取消它。

进度是可选的。服务器可以收下进度 token 却一条更新都不发。绝不能把"token 的存在"变成无限超时。

MCP 进度值必须递增。完成或取消后通知停止。给进度限速，防止快 worker 淹没传输。

> **【中文解读】** 双时钟防的是两种死法：只设空闲超时，持续发进度的僵死工作能永远续命；只设绝对超时，慢而合法的长任务会被误杀。进度重置空闲时钟、最大期限雷打不动，两者缺一不可。

## 请求取消不是 `tasks/cancel`

这些机制解决不同的生命周期。

| 机制 | 对象 | 信号 | 成功的含义 |
|------|------|------|------------|
| stdio 上的请求取消 | 一条在途 RPC | `notifications/cancelled` | 客户端放弃了请求；服务器应酌情停止 |
| HTTP 上的请求取消 | 一条在途响应流 | 关闭流 | 客户端放弃了请求；服务器应酌情停止 |
| `tasks/cancel` | 一个持久 Task | 普通 MCP 请求 | 服务器确认了取消意图 |

`tasks/cancel` 的成功结果并不证明 worker 已停止。Task 可能保持 `working`，直到某个 worker 检查点观察到取消标志；工作也可能在那个检查点之前完成。

HTTP 连接关闭时不要清除持久 Task 状态。创建 Task 的理由，就是它的生命周期比单个请求和单个连接都长。

> **【中文解读】** 一句话区分：请求取消面向"这条线上的消息"，`tasks/cancel` 面向"这件事本身"。UI 显示"已取消"只代表意图已确认；要看 Task 进入终态才算数。

## 新的 JSON-RPC ID 不等于幂等

JSON-RPC id 只关联请求与响应，不标识业务操作。

假设客户端用 id `41` 提交一笔扣款，丢了响应，再用 id `42` 重试。服务器看到两条不同的消息。没有应用层键，它无法知道它们是同一笔结算。

幂等键标识业务意图：

```json
{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}
```

服务器存储：

- 键；
- 操作参数的指纹；
- 已提交的结果。

同键同参返回存储的结果；同键不同参被拒绝——防止键被误用到另一个业务操作上。

> 💡 **【类比】** 幂等键像高铁购票的"订单号"。支付超时后重新发起支付用的是同一个订单号——系统认出这单已经出过票，直接把原来的票给你，而不是再扣一次款卖第二张。JSON-RPC id 则像每次点击生成的会话流水号：换个流水号重试，售票系统就当成全新的购买。

### 账本边界必须原子且持久

这个序列不安全：

```text
check key
run mutation
store result
```

两个 worker 都能观察到键缺失并都执行变更。效果之后、存储之前崩溃，会在重试时制造同样的歧义。

本课使用文件型 SQLite 账本。`BEGIN IMMEDIATE` 把键检查、模拟业务效果、执行计数和结果存储串进一个事务。两个独立的账本连接用同一个键竞争时，只会观察到一个已提交的结果和一次执行。关闭并重开账本，记录仍在。

每个返回值都从存储的 JSON 重建。调用方永远拿不到账本持有的可变对象，因此修改返回的字典污染不了后续重放结果。

模拟器的业务效果是同一 SQLite 事务内的回执和执行计数器。真实的支付、部署或外部 API 调用，不会因为写了一张本地表就变原子。生产需要可共享的持久数据库事务、事务性发件箱，或上游提供方强制同样的幂等键。仅靠进程锁既护不住多个副本，也活不过一次重启。

### 重试矩阵

实现重试之前先分类。

| 类别 | 示例 | 重试规则 |
|------|------|----------|
| 安全 | 无副作用的确定性读 | 理解失败边界后，可换新 JSON-RPC id 重试 |
| 有条件 | 带持久幂等键的变更 | 用同一个键和完全相同的参数重试 |
| 不安全 | 没有业务去重的变更 | 不要自动重试；先对账 |

`readOnlyHint`、`idempotentHint` 这类工具注解始终是不可信提示。重试安全由应用契约和服务器实现决定。

> **【中文解读】** 幂等三件套：键、参数指纹、已提交结果，缺一不可。只有键没有指纹，键被误用就会让两个业务意图互相串台；只有键和指纹没有持久存储，重启之后一切归零。

## 背压是正确性的一部分

SSE 生产者产生进度的速度可能快于客户端、代理或网络的消费速度。无界队列会把"慢"变成"内存耗尽"。

用有界队列，并定义什么可以丢。

进度是可替代的。同一 token 的后一个进度值取代前一个。最终的 JSON-RPC 响应不可替代。

本课的缓冲区应用这套策略：

1. 合并同一 token 的相邻进度。
2. 容量到达上限时丢最旧的进度。
3. 把流标记为需要权威重取。
4. 保住最终响应。
5. 拒绝"为保住一个最终响应而丢掉另一个最终响应"的状态。

这是有界丢失加显式恢复。静默丢失不是策略。

### 代理缓冲

服务器可能流式输出完全正确，而反向代理把事件攒在缓冲区里。

对 SSE 响应，发送：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

2026 Streamable HTTP 规范推荐 `X-Accel-Buffering: no`，让兼容的代理立即投递事件。

对安静的长连接流，周期性发送一条 SSE 注释：

```text
:
```

客户端忽略注释行。中间设备看到流量，就不太会关闭空闲连接。

保活不是进度。不要因为到达一条传输注释就重置操作的语义空闲超时。

> **【中文解读】** 背压策略的优先级铁律：进度可以丢（丢了就标记要重取），最终响应不能丢。`X-Accel-Buffering: no` 和注释保活解决的是中间设备这层——它们不认识 SSE，会把"没流量"当"死了"、把"流"当"文件"攒着发。

## 重连意味着重取

现代 Streamable HTTP 不支持通过 `Last-Event-ID` 恢复 SSE。

`subscriptions/listen` 流断开之后：

1. 用新的 JSON-RPC id 开一个新的监听请求。
2. 恢复期望的订阅过滤器。
3. 从权威方法重取受影响的 tools、resources、prompts 或 Tasks。
4. 按稳定标识符对应用状态去重。
5. 不要因为丢了响应就重放不安全的变更。

示例恢复计划显式把 `sendLastEventId` 设为 false，并列出要重取的资源。

### 防止重连风暴

如果一万个客户端在同一秒重连，正在恢复的服务器会再次倒下。

用带上限的指数退避加抖动。本课从客户端 id 和尝试序号计算确定性抖动，保证测试可复现：

```text
attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms
```

生产可以使用密码学安全或运行时随机性。不变量是分布形态，不是某个具体公式。

> **【中文解读】** "重连即重取"是 2026-07-28 规范的一个重要取向：流断了不续传，重新拉权威状态。这与很多 SSE 实现的 `Last-Event-ID` 续传习惯相反——迁移代码时最容易踩的坑。

## 动手实现

`code/main.py` 构建五个小型可靠性组件。

### `RequestCoordinator`

- 以空闲和最大双期限启动在途请求；
- 发出单调递增的进度通知；
- 产生正确的 stdio 或 HTTP 取消信号；
- 忽略非法的取消通知；
- 把取消与完成的终态竞态显式化；
- 把服务器方向的取消仅保留给 stdio 订阅。

### `MutationLedger`

- 证明没有业务键时，两个 JSON-RPC id 会执行两次；
- 用文件型 SQLite 事务串起键检查、模拟效果、执行计数和结果提交；
- 跨独立的账本连接，在同一幂等键下去重相同参数的调用；
- 拒绝同一键配合不同参数的重用；
- 返回防御性副本，并跨重开保留已提交记录。

### `DurableTaskService`

- 确认一个取消请求；
- 让任务保持 `working` 直到某个 worker 检查点；
- 演示为什么确认不是最终状态。

### `BoundedSseBuffer`

- 压力下合并或丢弃进度；
- 记录"需要权威重取"；
- 绝不丢弃最终响应。

### 恢复辅助

- 返回代理安全的 SSE 头和保活注释；
- 创建重连与重取计划；
- 用确定性的指数退避加抖动分散重试。

## 交互实验

不加任何 sleep，跑四种事件顺序。

1. 启动请求 `A`，取消它，然后调用 `complete()`。
2. 启动请求 `B`，完成它，然后送达取消。
3. 启动请求 `C`，在每个空闲期限前发进度，然后越过最大期限。
4. 在 Streamable HTTP 上启动请求 `D` 并关闭它的响应流。

每个场景记录：

- 请求的终态；
- 是否存在最终响应；
- 线上发出的取消信号；
- 客户端应该忽略哪个事件。

然后把 `D` 换成 stdio。操作完全相同，但取消信号必须换。

## 进阶练习

给 `MutationLedger` 加一个 `reserve_inventory` 变更。

要求：

1. 键绑定 SKU、数量、租户和操作名。
2. 同键同参的重试返回第一次预约。
3. 改了数量的重试失败，且不再产生预约。
4. 已提交但丢失响应的执行可以按键对账。
5. 结果不记录任何 secret 或支付数据。
6. 客户端没有提供键时，禁用自动重试。
7. 加一次模拟订阅断开，先重取库存记录再决定下一步。
8. 两个账本连接在 barrier 上启动，并发提交同一个键。断言只有一次预约被提交。
9. 修改第一次返回的预约对象。重放该键，证明存储结果没有变化。
10. 关闭并重开账本文件，然后按键对账预约。

保持实验诚实：如果库存在另一个服务里，说明该服务是否接受同一个幂等键，还是需要事务性发件箱把本地提交桥接到远端效果。

## 验证

以下陈述全部为真时，本课才算完成：

- stdio 取消发送 `notifications/cancelled` 且收不到响应。
- Streamable HTTP 取消关闭请求流，且不发送取消 POST。
- 先取消后完成会压掉最终响应。
- 先完成后取消保留响应并忽略迟到的取消。
- 进度能重置空闲超时，但永远动不了最大超时。
- 仅一个新的 JSON-RPC id 会再次执行变更。
- 同一个幂等键加相同参数，在双连接并发竞争下只执行一次。
- 已提交的记录经得起重开，重放返回防御性副本。
- 修改一个返回结果改变不了存储结果。
- 有界缓冲保持在容量之内，并保住最终响应。
- 重连使用新请求，不发送 `Last-Event-ID`，并重取受影响状态。
- `tasks/cancel` 确认之后，Task 保持非终态直到 worker 观察到它。

## 生产失败模式

| 失败 | 可观察症状 | 正确响应 |
|------|------------|----------|
| HTTP 客户端 POST 取消通知 | 服务器与客户端对请求生命周期各执一词 | 关闭该请求的 SSE 响应流 |
| 服务器在已接受的取消后仍响应 | 客户端收到不可用的迟到结果 | 取消获胜时停止工作并压掉后续消息 |
| 进度重置了每一个期限 | 僵死的工作永远活着 | 保留独立的绝对最大超时 |
| 新 RPC id 被当作去重 | 扣款、部署或删除执行两次 | 增加持久的应用幂等键 |
| 键检查与效果分离 | 并发 worker 都观察到键缺失 | 把键声明、效果记录和结果原子提交 |
| 内存账本跨副本使用 | 重启或另一个 worker 忘记先前提交 | 使用可共享持久存储或上游幂等 |
| 直接返回存储的可变结果 | 调用方的修改污染后续重放 | 序列化已提交结果并返回防御性副本 |
| 键被换着参数重用 | 一个键别到两个业务意图上 | 存储并比较参数指纹 |
| 无界进度队列 | 慢消费者在场时内存上涨 | 在界内合并并丢弃可替代的进度 |
| 压力下丢掉最终响应 | 客户端无法得知请求结局 | 为最终响应预留容量或驱逐进度，绝不驱逐它 |
| 代理缓冲 SSE | 进度成串到达或在超时后才到 | 关闭缓冲并为兼容代理配置超时 |
| 假设了 `Last-Event-ID` | 客户端从服务器不支持的状态恢复 | 用新请求重连并重取 |
| 每个客户端立刻重连 | 恢复制造了又一次宕机 | 使用带上限的指数退避加抖动 |
| Task 确认被当作最终取消 | UI 说停了、worker 还在跑 | 轮询 Task 直到终态 |

> **【中文解读】** 这张表按"症状→响应"组织，可直接当 on-call 手册用。注意一半以上的行都指向同一个根因：把"关联消息"的机制（RPC id、连接、确认）误当"业务安全"的机制（幂等键、原子提交、终态轮询）。

## 毕业项目衔接

工具生态毕业项目应把可靠性当作可执行的证据，而不是架构图里的一段文字。

要求这些工件：

- 每种传输一份取消竞态记录；
- 每个暴露变更的重试表；
- 一条幂等键记录和失配 fixture；
- 同键并发记录、重开检查和别名检查；
- 有界缓冲过载结果；
- 反向代理 SSE 头与空闲策略；
- 点名权威重取方法的重连计划；
- 毕业项目使用 Tasks 时的一份持久 Task 取消 trace。

本地进程里的一次绿色请求只证明了快乐路径。丢失响应、迟到取消、慢消费者和重连风暴都有确定性结局时，毕业项目才算生产就绪。

## 关键术语

| 术语 | 含义 |
|------|------|
| 请求取消（Request cancellation） | 放弃一条在途 MCP 请求 |
| 取消竞态（Cancellation race） | 终态完成事件与取消事件之间的竞争 |
| 空闲超时（Idle timeout） | 距上一次有用活动的时限 |
| 最大超时（Maximum timeout） | 从请求开始的绝对时限，不受进度影响 |
| 幂等键（Idempotency key） | 对一个业务意图去重的应用标识符 |
| 原子账本（Atomic ledger） | 把键声明、效果记录和结果作为一个单元提交的持久边界 |
| 背压（Backpressure） | 生产者快过消费者时施加的控制 |
| 进度合并（Progress coalescing） | 用更新的权威值替换较旧的进度 |
| 权威重取（Refetch） | 流断档后重新读取当前状态 |
| 抖动（Jitter） | 把重试在时间上摊开的刻意随机化 |
