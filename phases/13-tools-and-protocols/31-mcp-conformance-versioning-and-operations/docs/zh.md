# MCP 一致性工程：版本化、证据与运维

> 一个服务器不会因为"快乐路径在某个 SDK 里跑通了"就算一致（conformant）。一致性活在四个地方：线格式（wire）上、版本边界上、穿过中间设备时、以及回滚过程中。

> **【中文解读】** 本课是 MCP 2026-07-28 规范系列的收尾课：把规范性规则变成可执行的黄金/负面转录（transcript）语料库，把版本纪元、头部完整性、SDK 归一化差分、代理证据、脱敏、健康窗口与回滚证据全部接进一个发布门（release gate）。核心立场：一致性是一组可观察的不变量，必须赶在生产流量发现它们之前，先被测试架捕获。

> **【拓展：MCP→质量工程与 SRE】** 黄金样本与负面测试、降级攻击防护、透传代理差分、发布门与证据化回滚——每个手段都是协议工程与 SRE 的经典课题（HTTP/TLS 一致性套件、降级保护、金丝雀发布都是同构问题）。本课把它们对准 MCP 的具体契约：`resultType` 判别器、镜像路由头、通知不变量、以及 2026-07-28 的自包含元数据。它与 Phase 13 · 29（可靠性）和 Phase 13 · 30（注册中心准入）首尾相接：29 管"出事了怎么活"，30 管"进门前怎么审"，本课管"凭什么说它一直是对的"。

> 🔗 **【前置】** 学本课前请先掌握：Phase 13 · 09（MCP 传输——Streamable HTTP 与头部）、Phase 13 · 17（网关与注册中心——中间设备与镜像头）、Phase 13 · 30（注册中心准入——pin、证据摘要与回滚目标）。

## 学习目标

- 把规范性的 MCP 规则变成黄金与负面线格式转录（transcript）。
- 让严格的 `2026-07-28` 行为与有界的旧版回退（legacy fallback）保持分离。
- 区分"增量式未知字段"与"非法的未知 `resultType`"。
- 把原始 JSON-RPC 证据与 SDK 归一化后的视图做差分比较。
- 穿过真实的代理边界证明头部与主体的完整性。
- 用脱敏后的转录、健康与回滚证据为发布把关。

## 问题引入

你的客户端通过 SDK 调用 `tools/list` 并拿到了工具，集成测试通过了。

这个结果留下了许多没有回答的重要问题：

- 请求带没带现代的逐请求协议元数据？
- `MCP-Protocol-Version`、`Mcp-Method` 和 `Mcp-Name` 与 JSON-RPC 主体一致吗？
- 响应在线上真的带了合法的 `resultType`，还是 SDK 合成的？
- 客户端会保留未来新增的增量字段吗？
- 一个被识别的现代错误会不会意外触发旧版握手？
- 代理保住了源站状态码和 JSON-RPC 错误吗？
- 通知序列化器有没有吐出被禁止的响应？
- 运维能不能在不存 secret 的前提下，证明一次发布或回滚的理由？

一致性是一组可观察的不变量。在生产流量不得不发现它们之前，先构建一个能捕获这些不变量的测试架。

```figure
mcp-conformance-operations
```

> **【中文解读】** 这份问题清单就是全课的目录：逐请求元数据与纪元选择（下节）、头部与主体一致性、未知字段与判别器、SDK 差分、代理证据、脱敏、健康与回滚门。每一节都把清单里的一两个问题变成可断言的负面用例。

## 从版本纪元开始

MCP `2026-07-28` 使用自包含的逐请求元数据。现代请求携带 `params._meta.io.modelcontextprotocol/protocolVersion` 和 `params._meta.io.modelcontextprotocol/clientCapabilities`。精确的命名空间键很重要：裸的 `protocolVersion` 或 `clientCapabilities` 别名是畸形的。镜像路由头出现在 HTTP 边界时，其值必须与 JSON-RPC 主体一致。现代成功结果携带 `resultType`。

截至 `2025-11-25` 的版本使用更早的初始化纪元。一个没有 `resultType` 的旧版结果，只有在客户端已经选定那个更早纪元之后，才会被解释为 complete。

不要做一个"同时接受两种形态"的宽松验证器。用两个分支：

| 分支 | 入口证据 | 缺失 `resultType` | 初始化 |
|---|---|---|---|
| 现代 | 成功的 `server/discover` 或被识别的现代响应 | 非法 | 不是默认路径 |
| 旧版 | 已配置的 allowlist 加一次无结论现代探测之后有效的旧版 `initialize` 结果 | 解释为 complete | 该纪元必需 |

这种分离防止一个畸形的现代对端反而获得更弱的验证。

> **【中文解读】** 两个纪元两套规则。分开的分支是安全边界：现代对端必须给出正面证明（成功的 `server/discover` 或被识别的现代错误），拿不出证明就修正请求或停止——绝不能因为 `-32020/-32021/-32022` 而降级。回退模式先做一次有界现代探测，超时/空响应/断连只是"无结论"、不证明旧版；只有显式 allowlist 的端点才可做有界旧版探测，且必须验证其 `initialize` 结果后才选定旧分支。把选定的纪元记录在每条转录旁边——没有这个事实，同一个缺失字段可能这次测试看着合法、下次就非法。

> 💡 **【类比】** 版本纪元像充电口的"全程 USB-C"与"备用转接头"。默认只走 USB-C（严格模式）；转接头（旧版回退）只给登记在白名单里的老设备用，而且要先确认那台设备真的是老设备（合法的 legacy `initialize` 证据）——不能因为"新线没插上"（超时/无响应）就默认对方是老设备。否则一个干扰你的中间人就能靠"弄丢现代响应"把整个连接拖回旧协议，这正是降级攻击（downgrade attack）的套路。

### 严格模式

严格模式要求现代行为的正面证明：一次成功的 `server/discover` 证明现代分支，一个被识别的现代 JSON-RPC 错误同样证明它。修正请求或直接停止——绝不因为服务器返回 `-32020`、`-32021` 或 `-32022` 而降级。

### 回退模式

回退模式先做一次有界的现代探测。超时、空响应、断连或无法识别的响应都是"无结论"——它们不证明对端是旧版。只有被显式配置或列入兼容 allowlist 的端点，才可以接收一次有界的旧版探测；而且客户端只有在验证了那次探测的 `initialize` 结果与协商出的旧版修订之后，才选定旧分支。

回退不是"任何错误之后都试试旧版"。一个被识别的现代错误携带有用的修正信息；在它之后降级，可能掩盖头部不匹配、能力声明缺失或版本不受支持。

这防止攻击者、故障或过滤型代理靠"弄丢现代响应"强迫降级。要把端点策略、无结论的现代观察、确切的旧版正面证据和选定的纪元记录在一起。

把选定的纪元记录在每条转录旁边。没有这个事实，同一个缺失字段可能这一次测试运行看着合法、下一次就变成非法。

## 构建转录语料库

一条转录 fixture 记录的是跨过边界的内容，而不只是那次 SDK 调用：

```json
{
  "name": "golden-modern-list",
  "era": "modern",
  "headers": {
    "MCP-Protocol-Version": "2026-07-28",
    "Mcp-Method": "tools/list"
  },
  "request": {
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/list",
    "params": {
      "_meta": {
        "io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {}
      }
    }
  },
  "responseStatus": 200,
  "responseBody": {
    "jsonrpc": "2.0",
    "id": 1,
    "result": {
      "resultType": "complete",
      "tools": []
    }
  }
}
```

保留两类 fixture。

### 黄金转录

黄金转录证明"被接受的行为"：

- 带匹配元数据与头部的现代 discovery 或方法请求
- 带必需字段的 complete 结果
- 方法可以请求更多输入时的 `input_required` 结果
- 只在对应能力已声明之后的扩展结果
- 没有 `resultType` 的旧版结果，但仅在选定的旧纪元里
- 通知被处理且没有 JSON-RPC 响应

黄金转录要精确，不要庞大。把易变的 ID 与时间戳做成确定性的，或在比较前先规范化。

### 负面转录

负面转录证明"被拒绝的行为"：

- 头部与主体不匹配
- 缺失逐请求能力
- 不受支持的已匹配协议版本
- 缺失现代 `resultType`
- 未知或未声明的 `resultType`
- 响应 `jsonrpc` 不是 `2.0`，或 ID 在值或 JSON 类型上不一致
- 响应同时含 `result` 和 `error`，或两者都没有
- 错误缺少整数 `code` 和字符串 `message`
- 已知协议错误映射到了错误的 HTTP 状态
- 为通知发出了响应
- 畸形的 JSON-RPC 信封
- 代理坍缩了协议错误

对每条负面用例，断言拒绝边界和稳定的错误码。"调用失败了"太弱——代理生成的 500 与源站的 `-32020` 看起来都像失败，但它们讲给运维的故事完全不同。

头部不匹配的 fixture 必须包含服务器真实的 HTTP 400 JSON-RPC 响应——带匹配的请求 ID 和错误码 `-32020`。只要本地验证器观察到 `HeaderMismatch`，就自动强制这一点；不要把响应校验做成可选的 fixture 开关。一个"HTTP 500 且无响应体"的用例，即使本地拒绝码是对的也算失败。一个在自己的请求验证器抛出异常之后就停下的测试架，只测试了它自己，没有测试服务器的线上行为。

官方 MCP 一致性项目适合作为外部套件和带版本的参照。但本地的转录也要保留：它们捕获的是你的代理、SDK、认证、扩展与发布路径——这些是一般性套件不可能知道的。

> **【中文解读】** 语料库的两类 fixture 各证一半：黄金证"该接受的确实接受了"，负面证"该拒绝的确实拒绝了、且以正确的错误码拒绝"。最容易被跳过的检查是负面用例的服务器响应侧——测试架必须读完整台服务器的真实响应，不能只验证自己的请求验证器抛了异常。

## 头部值必须与 RPC 主体一致

在现代 Streamable HTTP 中，中间设备可以用镜像头部做路由或执行策略，但 JSON-RPC 主体仍是协议的事实来源。不匹配是完整性故障，不是"提示你挑一个值"。

按以下顺序验证：

1. 解析并校验 JSON-RPC 信封与元数据类型。
2. 比对 `MCP-Protocol-Version` 与 `params._meta.io.modelcontextprotocol/protocolVersion`。
3. 比对 `Mcp-Method` 与 `method`。
4. 方法带路由名时，比对 `Mcp-Name` 与对应的主体值。
5. 相等确立之后，才判断已匹配的版本与能力集是否受支持。

这个顺序把不匹配 `-32020` 与版本不受支持 `-32022` 区分开，也阻止了"网关按头部名字授权、而源站执行另一个主体名字"的情况。

HTTP 字段名大小写不敏感，而值保持大小写敏感。查找前先规范化头部名，并拒绝冲突的重复头。`Mcp-Name` 含不安全、非 ASCII 或首尾空白字符时，先解码精确的 `=?base64?{Base64EncodedValue}?=` UTF-8 哨兵，再与主体比较。不完整的哨兵、非法 Base64、非法 UTF-8 或原始不安全值都以 `-32020` 拒绝。即使主体含有相同字符，原始的首尾空白也非法——因为那个值在传输前必须经过哨兵编码。

中间设备可以在请求到达 MCP 服务器之前拒绝畸形 HTTP，所以它的失败可能是没有 JSON-RPC 的 HTTP 错误。捕获一次拒绝来自中间设备还是源站。源站 MCP 服务器在处理了合法 JSON-RPC 请求时，应使用协议错误契约。

> **【中文解读】** "先证相等、再谈支持"是这个顺序的精髓：不相等是完整性问题（`-32020`），相等但版本不受支持是版本问题（`-32022`），两者的修复动作完全不同。`Mcp-Name` 的 Base64 哨兵机制则堵住了"网关授权一个工具名、源站执行另一个"的越权路径。

## 未知字段不等于未知结果

前向兼容需要两条不同的规则。

### 增量式未知字段

result 对象与 `_meta` 映射可以新增字段。验证器应根据自身角色保留或忽略增量字段，除非该字段违反了保留契约。示例把完整原始结果留在证据里，并接受已知结果旁边的 `futureHint`。

如果你是透明代理，保留未知字段通常比剥掉它更安全；如果你是应用客户端，忽略它可以合法。但差分测试仍应揭示"SDK 略过了它"，让这个行为成为有意为之。

### 未知的 resultType

`resultType` 是一个判别器。核心现代结果使用 `complete` 或 `input_required`；扩展只有在对应能力已被声明的情况下才能新增别的值——例如 Tasks 扩展在协商出的能力上下文里可以新增 `task`。

未知或未声明的判别器不能被安全地当作 complete。客户端不知道自己将丢弃怎样的生命周期。拒绝它。

因此，同一份原始响应可以既包含可接受的未知字段、又包含不可接受的未知结果类型。两种情况都要测。

判别器只是第一层，其后还要校验方法特定的载荷：complete 的 `tools/list` 结果需要 `tools` 数组，描述符要有唯一非空名字、有用的描述和对象根的 `inputSchema`；`task` 结果只有在带 Tasks 能力的合规 `tools/call` 里才合法，需要 `taskId`、已知状态、创建与更新时间戳和 `ttlMs`，外加合法的可选轮询间隔；complete 的 `completion/complete` 结果需要 `completion` 对象——字符串值不超过 100 个、可选的非负整数 `total` 不得小于返回值数量、可选的布尔 `hasMore`。拼写正确的 `resultType` 救不了畸形的载荷。

> **【中文解读】** "未知"在不同位置含义不同：result 里的未知字段是未来的扩展空间（保留或忽略都可以，但要显式决定）；`resultType` 里的未知值是未知的生命周期（绝不能当 complete 处理，必须拒绝）。判别器合法之后还要过载荷校验——三层各管一段，缺一不可。

## 通知不变量

一条 JSON-RPC 通知没有 `id`。接收方不得发送 JSON-RPC 成功或错误响应。

对被接受的 HTTP 通知形态，测试架期望 HTTP `202` 和空主体。MCP `2026-07-28` 没有定义核心的客户端到服务器 Streamable HTTP 通知。示例使用一个命名空间的课程扩展通知，只为测试单向序列化器不变量；不要把它当成新的核心方法。

测序列化器，而不只是处理器。处理器可能返回 `None`，而中间件把它包成一个 JSON 成功对象。捕获最终的出口字节。

## 增加 SDK 差分

SDK 常把线上对象转成方便的语言类型。这很有用，但一个归一化的对象证明不了实际收到了什么。

对每条高风险 fixture，捕获：

1. SDK 解码前的原始状态、头部与响应体。
2. SDK 归一化的返回值或异常。
3. 选定纪元的期望语义投影。
4. SDK 抬升、合成、剥除或改变了的字段。

示例允许 SDK 专门移除已知的线上簿记字段（如 `resultType`、`_meta`、`ttlMs`、`cacheScope`），并同时比较应用载荷；但 `futureHint` 被丢弃要如实报告——那个未知语义字段消失了。

不要假设每一处差异都是 SDK bug。差分的意义是让转换可见。先想清楚你的组件是"可以忽略增量字段的应用端点"，还是"应当保留它的透明中间人"。

对你发布的每一个 SDK 与版本运行差分。如果两个 SDK 对同一转录的归一化不同，发布策略应当写明哪种行为可接受，而不是事后挑最顺手的输出。

> **【中文解读】** 差分测试的四样捕获物里最关键的是第四样——"SDK 改了什么"的显式清单。有了它，"SDK 丢了字段"从隐式行为变成显式决策：要么写进发布策略说可接受，要么算阻塞问题。两个 SDK 归一化不一致时，规则是先定标准、再选实现，而不是反过来。

## 捕获代理证据

大多数生产 MCP 故障跨越不止一个进程。记录三个视角：

| 视角 | 最少证据 |
|---|---|
| 入口（Ingress） | 请求头部、JSON-RPC 主体、内容类型、已认证路由、接收时间 |
| 源站（Origin） | 转发的头部与主体摘要、源站状态码、响应头部与主体 |
| 出口（Egress） | 客户端可见的状态码、头部、主体与发送时间 |

示例检测两类常见变换：

- 源站的 HTTP 400 或 404 JSON-RPC 错误变成代理的通用 500
- 出口 JSON-RPC 主体与源站主体不一致

再为内容类型、`Accept`、压缩、请求级 SSE、缓存头和 trace 关联加上部署特定的断言。策略允许时捕获 TLS 终止的两侧。绝不要为了证明路径而记录凭证。

## 证据离开内存前先脱敏

脱敏是一致性运维的一部分，不是之后的清理工作。在序列化、哈希、日志、测试工件或失败上传之前完成它。

示例先把键名做大小写折叠并移除分隔符再匹配，然后递归替换 `Authorization`、`Cookie`、`Set-Cookie`、`X-Api-Key`、`accessToken`、`clientSecret`、`registrationAccessToken`、`token`、`password`、`secret`、`api_key` 等键下的值。规范化与 denylist 必须使用同一种形态，这样 camelCase、连字符、下划线和点号变体就无法互相绕过对方的策略。生产采集器还应增加方法特定的参数策略，因为像 `query` 这样无害的键仍可能携带个人或受监管数据。

对脱敏后的证据包做哈希。只有特定调查确实需要时，才把原始抓拍保留在受批准的短生命周期系统里。摘要证明的是哪一份脱敏包驱动了决策；它不会泄露被移除的值。

> **【中文解读】** 脱敏的两个工程要点：一是时机——必须发生在序列化/哈希/日志之前，"先存后清"总会漏；二是形态统一——键名规范化与 denylist 用同一种折叠形态，否则 `apiKey` 混过 `api_key` 的检查。哈希脱敏包而非原始包，让"哪份证据驱动了决策"可验证而不泄密。

## 把健康与回滚纳入发布门

协议一致是发布的必要条件而非充分条件。一个一致的候选版本仍可能超时、泄漏内存或压垮某个依赖。

发布之前先定义健康窗口：

- 最小样本数
- 最大错误率
- 最大延迟分位
- 饱和或资源上限
- 观察时长
- 与已准入基线的比较

发布之前同样定义回滚证据：

- 精确的先前版本
- 准入证据摘要
- SHA-256 制品与描述符 pin
- 当前 Registry 状态
- 当前健康结果
- 路由恢复程序
- 一个可信发布控制器身份对以上精确字段的一次认证（attestation）

要求回滚目标在晋升之前就完成验证并且健康，而不是只等候选失败之后才查。一次没有可用恢复路径的成功发布并不算生产就绪。

如果候选失败而回滚目标缺少证据，那就稳住流量，不要去猜。"回到之前随便哪个版本"不是一种运维控制。

不要把就绪检查退化成真值判断——比如非空的版本号、`healthy: "yes"` 或任意的证据字符串。示例要求精确类型、active 状态、三个 SHA-256 摘要、可信签名者，以及对完整回滚载荷的有效 HMAC-SHA-256 认证。它确定性的 demo 密钥是非机密 fixture；生产中要在发布边界注入受保护的密钥、KMS 验证结果或公钥认证验证器。

发布门还拒绝空的转录、SDK 差分或代理证据：每个来源都必须携带有效的证据摘要。一个绿了的健康窗口，填不上一个从未被观察过的边界。

> **【中文解读】** 发布门的五个证据来源缺一不可：转录（协议行为）、SDK 差分（语义转换）、代理（中间设备）、健康（运行时表现）、回滚证据（恢复路径）。最容易造假的是最后两个——所以示例把回滚就绪做成了类型精确、带 HMAC 认证的字段集合，而不是一个布尔。回滚目标必须在晋升前就已验证，这把"恢复能力"从事后补救变成了发布前置条件。

## 动手实现

运行标准库测试架：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
```

demo 恰好运行十五条黄金与负面转录（含合法与畸形的 completion 结果），把原始结果与 SDK 视图做比较，检视一个吞掉了源站错误的代理，评估健康，认证回滚证据，并选中该目标。

预期输出形状：

```json
{
  "transcriptsPassed": 15,
  "transcriptsTotal": 15,
  "sdkDroppedFields": ["futureHint"],
  "proxyIssues": [
    "proxy collapsed a protocol error into HTTP 500",
    "proxy changed the origin JSON-RPC body"
  ],
  "releaseAction": "rollback",
  "evidenceDigest": "..."
}
```

按以下顺序阅读 `code/main.py`：

1. `validate_request()` 执行纪元特定的请求与头部规则。
2. `validate_result()` 区分缺失的旧版判别器、合法现代值、扩展与未知值。
3. `select_era()` 实现严格与有界回退策略。
4. `run_transcript()` 评估黄金与负面 fixture。
5. `compare_sdk_view()` 暴露归一化差异。
6. `inspect_proxy()` 比较入口、源站与出口证据。
7. `redact()` 在证据哈希前移除显性 secret。
8. `rollback_evidence_ready()` 校验精确的 pin 字段与可信发布认证。
9. `ReleaseGate.evaluate()` 拼接非空的 conformance、SDK、代理、健康与回滚证据。

## 用框架实现

在四个时间点运行测试架：

1. 每次实现改动时，用进程内测试适配器。
2. 对构建出的客户端与服务器二进制，走真实传输。
3. 在 staging 环境里穿过部署好的代理或网关。
4. 金丝雀发布期间，带真实的健康与回滚证据。

在各层之间保持相同的稳定用例名：`negative-header-body-mismatch` 在单元、端到端、代理和金丝雀报告里必须指同一个不变量。证据摘要会不同——因为边界变了；但要求不能变。

fixture schema 存进版本控制；脱敏后的运行证据存进发布系统；短生命周期的原始抓拍只放在事件访问控制之下。

## 交互实验

### 实验 A：证明纪元边界

从 `code` 目录打开 Python：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations/code
python3 -q
```

运行：

```python
from main import *
validate_result({"tools": []}, "legacy")
validate_result({"tools": []}, "modern")
```

旧版调用推断出 `complete`；现代调用抛出 `ProtocolViolation`。接着测回退：

```python
select_era({"kind": "timeout"}, "fallback")
select_era(
    {"kind": "timeout"},
    "fallback",
    legacy_allowed=True,
    legacy_evidence={"kind": "initialize_success", "protocolVersion": LEGACY_VERSION},
)
select_era({"kind": "jsonrpc_error", "code": -32021}, "fallback")
```

第一个超时失败闭合（fail closed），因为沉默不是旧版证据。第二个调用之所以能选定旧版，只是因为配置允许、且观察到了一个有效的旧版初始化结果。而被识别的"能力缺失"错误证明的是现代分支。

### 实验 B：增量字段与判别器

```python
validate_result({"resultType": "complete", "tools": [], "futureHint": True}, "modern")
validate_result({"resultType": "future_mode", "tools": []}, "modern")
```

第一个结果保留了 `futureHint`；第二个被拒绝，因为生命周期判别器是未知的。

### 实验 C：检视 SDK 转换

```python
compare_sdk_view(
    {"resultType": "complete", "tools": [], "futureHint": {"mode": "new"}},
    {"tools": []},
)
```

决定你的组件可以忽略 `futureHint`，还是必须转发它。把这个选择写进发布策略，不要悄悄抹掉差分结果。

### 实验 D：修复代理

修改 demo 交换，让出口保留源站状态码与主体。再跑一次 `python3 main.py`：代理问题应该消失，但 SDK 差分仍然挡住晋升。然后把 `futureHint` 加进 SDK 视图，观察当每个证据来源都通过时，动作变成 `promote`。

## 进阶练习

给测试架增加请求级 SSE 转录。

要求：

- 捕获响应状态、内容类型、有序 SSE 事件与流终止。
- 证明每个 JSON-RPC 事件都有合法的纪元特定结果或错误。
- 为"把整个流缓冲完再转发"的代理加一条负面用例。
- 为 JSON-RPC id 与请求不符的 SSE 事件加一条负面用例。
- 写证据前先脱敏事件数据。
- 把流时长、首事件延迟和事件计数纳入健康窗口。
- 流失败时，让发布门只选有证据的回滚目标。

成功的标准：同一条用例既能直连运行也能穿代理运行，报告能指出改变行为的精确边界。

## 验证

运行 demo 与确定性测试套件：

```bash
cd phases/13-tools-and-protocols/31-mcp-conformance-versioning-and-operations
python3 code/main.py
python3 -m unittest discover -s code/tests -v
```

验证应证明：

- 所有黄金与负面转录都到达预期结局
- 现代请求要求精确的命名空间元数据键
- HTTP 头部名大小写不敏感地匹配、编码的 `Mcp-Name` 值被精确解码
- 头部与主体不匹配返回现代不匹配码
- 响应版本、ID、result/error 互斥、错误形态与 HTTP 映射都被校验
- 方法特定的 tool-list、task 与 completion 载荷要求被执行
- 每个观察到的 `HeaderMismatch` 都要求真实的 HTTP 400 JSON-RPC `-32020` 响应
- 原始 `Mcp-Name` 空白被拒绝，而哨兵编码的空白精确往返
- 缺失 `resultType` 只在选定的旧纪元合法
- 增量字段在原始校验中存活，而未知结果类型失败
- 扩展结果类型要求其能力已声明
- 被识别的现代错误绝不触发旧版回退
- 通知不产生 JSON-RPC 响应
- SDK 簿记移除与语义字段丢失被区分
- 代理错误坍缩被检测，凭证在 camelCase 与分隔符变体上被递归脱敏
- 晋升要求非空的转录、SDK、代理与健康运维证据
- 晋升与回滚都要求一个已认证、已 pin、active、健康的回滚目标

## 生产失败模式

| 失败 | 弱测试会报告什么 | 测试架必须证明什么 |
|---|---|---|
| SDK 合成了缺失的判别器 | "tools/list 通过了" | 原始现代结果缺 `resultType`，非法 |
| 客户端在 `-32021` 后降级 | "旧版重试成功了" | 被识别的现代错误禁止回退 |
| 未知结果类型被当作 complete | "响应解析成功" | 未声明的生命周期判别器被拒绝 |
| 代理授权一个工具、源站执行另一个 | "请求到达了服务器" | `Mcp-Name` 在每一跳都等于主体路由名 |
| 测试架在读到服务器响应前就抛出 | "头部不匹配测试通过了" | 捕获并校验 HTTP 400 与 JSON-RPC `-32020` 响应 |
| 代理把源站 400 变成通用 500 | "上游错误" | 源站与出口的状态码和 JSON-RPC 主体都被保留 |
| 通知中间件吐出 `{result: null}` | "处理器返回了 none" | 最终出口主体为空且无 JSON-RPC 响应 |
| SDK 剥掉一个增量字段 | "类型化对象匹配" | 原始与归一化视图给出精确的丢失字段 |
| 失败工件泄漏 bearer token | "调试包已上传" | 脱敏发生在哈希、日志或上传之前 |
| 凭证键风格绕过脱敏 | "denylist 里有 api_key" | camelCase 与分隔符变体共用一种规范化 denylist 形态 |
| 金丝雀零样本却显示健康 | "零错误" | 最小样本数被强制 |
| 回滚选中一个未知构建 | "之前的部署已恢复" | 目标版本、准入摘要、pin、状态与健康齐备 |

> **【中文解读】** 这张表的阅读方法：中列是"弱测试给你的假安心"，右列是"测试架必须给出的真证据"。一半以上的行指向同一类根因——在错误的层（SDK 对象、代理日志、布尔健康位）上做验证，而没有回到线格式本身。

## 运维准则

测试你发出的字节、每个中间设备转发的字节、每个 SDK 暴露的语义，以及运维在压力之下要用的证据。兼容是一个显式分支；回滚是一个有证据支撑的发布动作。两者都不应该是宽松解析器意外产生的副作用。

> **【中文解读】** 一句话总结全课：一致性不是"跑通一次"，而是"每个边界都有可观察、可复现的证据"。宽松解析器会把"兼容"和"回滚"都变成意外的副作用；显式分支加证据化决策，才把它们变回受控的工程行为。
