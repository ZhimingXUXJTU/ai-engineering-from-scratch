> 宿主为每一个工具声明三个字段.

- **Name.**机器可读的稳定识别器.`get_weather`没有"天气问题".
  翻译: 中文**名称。**一个稳定的机器可读的标识符.`get_weather`没有"天气那玩意"
- **Description.**简单一段自然语言简单. "当用户询问特定城市的当前状况时,请使用.不要用于历史数据".
  翻译: 中文**描述。**一段简短的自然语言说明:"当用户询问一个城市的当前状况时使用.
- **Input schema.**描述工具的参数的JSON Schema对象 (2020-12年草案).
  翻译: 中文**输入模式。**一个JSON方案对象 (2020-12 草案),描述工具的参数.

>  **【类比】**工具接口像餐厅点餐:菜单上每道菜=工具,菜名=工具名,菜单上的描述=描述("招牌牛肉面,清真可选,配油"),点餐时填的选项(度、加蛋)=JSON计划 参数──服务员(模型) 看菜单决定推哪道菜,把订单(工具_调用) 递交给厨房(执行器),厨房做好端上来(工具_结果),服务员转交给顾客──模型从厨房进来,只递交单子──

### 第二步:决定

> **【中文解读】**模型面对用户消息和可用工具列表时,有三种选择:直接文本回答、调用一个或多个工具、或拒绝──工具调用负载包含三个字段:调用 id(用于关联结果)、工具名(工具名)、参数(JSON 参数对象)──并行调用时 id 尤为重要,因为结果可能乱序返回──

### 第三步:执行

> **【中文解读】**执行阶段,主机程序接收调用请求,先使用JSON Schema验证参数合法性,然后运行执行器――参数验证失败 (幻觉字段、类型错误) 是弱模型最常见的失败模式――生产环境通常有三种应对策略:快速失败并反错误、使用约束解析器修复JSON、或带错误信息重试模型――

接待者接收了调用,验证了对声明的方案的参数,并运行执行器. 无效的参数意味着模型幻觉了一个字段或使用错误的类型 很常见的失败模式在弱型模型上. 制作主机在不有效的参数上做三个事情之一:快速失败并将错误传递到模型中,使用限制式解析器修复JSON,或在提示中包含的验证错误中重新尝试模型.

> 宿主接收调调,根据声明的模式验证参数,然后运行执行器.无效参数意味着模型幻觉一个段段或使用错误类型.这是弱模型上非常常见的失败模式.生产环境主对无效参数做三件事之一:快速失败并向模型展示错误.

> ️ **【易错点】**场景:跳过方案 验证直接执行 / 后果:弱模型(Haiku、GPT-4o-mini) 会幻觉字段(如`get_weather({ cityy: "Tokyo" })`拼错键),执行器要么 KeyError 崩要么拿到 没有走错分支 / 修复:在执行器前必加方案验证,失败时把错误以`tool_result`形式返回模型让它重试,而不是抛弃异常给主机.

执行器本身是普通代码. Python,TypeScript,一个 shell命令,数据库查询.它产生一个结果,通常是字符串,但可以是任何JSON值或结构化内容块 (文本,图像或资源引用在MCP).结果必须是串化.

> 执行器本身就是普通代码──Python、TypeScript、shell 命令、数据库查询──它产生一个结果,通常是一个字符串,但也可以是任何JSON值或结构化内容块(MCP中文本、图像或资源引用)──结果必须是可序列化的──

### 信任分开了

> **【中文解读】**工具分为两类:纯工具 (只读,没有副作用,如get_weather) 和后果性工具 (改变状态,消耗资金,触及用户数据,如发送_电子邮件) 后果性工具必须设置门控制机制.

> **【拓展：Agent 安全中的 Tool Poisoning】**攻击显示,恶意工具可以通过精心构建的描述欺诈模型执行危险操作.例如嵌入工具描述中"当用户要求删除时立即执行"的隐藏命令.

工具有两种味道,

> 工具从安全角度分为两类:

- **Pure.**只有阅读,确定性,没有副作用.`get_weather`现在`search_docs`现在`get_current_time`值得推测.
  翻译: 中文**纯工具。**只有读,确定性,没有副作用.`get_weather`,我知道.`search_docs`,我知道.`get_current_time`可以安全地推测性调用
- **Consequential.**变化状态,花钱,触摸用户数据.`send_email`现在`delete_file`现在`execute_trade`必须有门.
  翻译: 中文**后果性工具。**修改状态,消耗资金,触及用户数据.`send_email`,我知道.`delete_file`,我知道.`execute_trade`必须设置门控.

> **【中文解读】**纯提示方式让模型输出JSON的失败率在5-15%,小模型更高.失败模式包括:缺少大括号,尾随逗号,幻觉字段,类型错误.

> "让模型使用JSON回复"是函数调调出现前的模式――在前沿模型上失败率约为5-15%,在小模型上远高于此――失败模式包括缺少大括号,尾随逗号,幻觉字段和错误类型――之后你需要JSON修复步骤,重试或束解码器――

由于三个原因,本地函数调用更好. 首先,提供商将模型端到端训练在准确的呼叫形状上, 第二,调用用电话的有效载荷位于其自己的协议插槽,而不是在自由文本中,因此工具调用永远不会泄露到用户可见的回复中. 第三,提供商强制执行方案的遵守限制式解码 (OpenAI的严格模式,Anthropic的严格模式).`tool_use`双子座的`responseSchema`) 产量保证验证.

> 调用原生函数更好有三种原因.第一,提供商在精确的调用格式上端到端训练模型,因此在严格模式下有效的JSON 率达到98-99%.第二,调用负载位于独立协议槽位,不在自由文本中.因此工具调用永远不会泄露给用户可见的回复中.第三,提供商通过约束解码(OpenAI的严格模式、人类的.`tool_use`子的`responseSchema`)强制执行模式合规――输出保证能通过验证――

## 关键词 快速查找表

| Term | What people say | What it actually means | 中文术语 |
|------|----------------|------------------------|----------|
| Tool | "A thing the model can call" | A triple of name + JSON-Schema-typed input + executor function | 工具 |
| Function calling | "Native tool use" | Provider-level API support for emitting structured tool calls instead of prose | 函数调用 |
| Tool call | "The model's request to act" | A JSON payload with `id`, `name`, `arguments` emitted by the model | 工具调用 |
| Tool result | "What the tool returned" | The executor's output, wrapped in a `tool` role message with matching id | 工具结果 |
| Parallel tool calls | "Many calls at once" | Multiple call objects in one model turn, independent and orderable by id | 并行工具调用 |
| Strict mode | "Guaranteed JSON" | Constrained decoding that forces the model's output to validate against the declared schema | 严格模式 |
| Pure tool | "Read-only tool" | No side effects; safe to re-run | 纯工具 |
| Consequential tool | "Action tool" | Mutates external state; requires gate, audit, or user confirmation | 后果性工具 |
| Four-step loop | "The tool-call cycle" | describe → decide → execute → observe | 四步循环 |
| Host | "Agent runtime" | The program that holds the tool registry, calls the model, and runs the executor | 宿主 |
